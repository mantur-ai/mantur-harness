# Agent Note: Mantur Fork 开发规范

Status: implemented

[English](2026-09-02-mantur-fork-development-policy.md) | 中文

## 问题

Mantur 版需要在持续获取 DSH 官方更新的同时，为 DeepSeek Harness 增加漫剧生产能力。如果没有明确的代码归属和 Git 规则，日常功能开发容易侵入官方核心模块，累积私有补丁，或让官方合并与产品改动无法区分。含糊的提交信息还会迫使维护者先打开差异，才能理解历史。

## 决策

Fork 以 `origin/main` 作为稳定的漫剧分支。本地 `master` 跟踪 `upstream/master`，代表 DSH 官方底座。功能和缺陷开发分别使用 `feat/<topic>` 和 `fix/<topic>` 分支；共享分支通过 merge 接收更新，不改写已发布的历史。

漫剧能力优先归属于插件、Skill、profile 或配置覆盖层以及已记录的扩展点。只有这些机制无法表达已验证的需求时，才允许修改官方核心代码。该改动必须记录扩展点为何不足、受影响的官方文件，以及下次合并官方更新时的验证方式。

每个分支只包含一个可评审的功能或修复。代码、聚焦的验证证据、文档和必需的 Agent Note 同步变更。无关清理和推测性基础设施不进入该改动。

每次提交的标题使用 `<type>(<scope>): <plain outcome>`；当 scope 不能提供有用信息时可省略。标题需要用通俗语言说明实际结果。如果仅看标题不能理解改动，提交正文就用 `Changed:` 和 `Why:` 做简短说明。不接受 `update`、`misc`、`fix stuff` 和 `WIP` 等笼统标题。

## 验证

发布前，作者需要检查完整差异，通过仓库的推送前流程运行覆盖改动的最小检查集，并报告未运行的检查。官方更新从 `upstream/master` 合并到本地 `master`，再合并到 `main`；只有所选检查通过后才发布 Fork。

## 曾考虑的替代方案

**只要开发更快就修改官方核心。** 这种做法可能缩短一次实现，但会扩大每次 DSH 更新的冲突范围，并隐藏哪些能力属于 Mantur。

**仅保留 Fork 远程。** 这会让官方更新更难识别，并弱化 DSH 底座与漫剧改动之间的区分。

**允许任意提交标题。** Git 会接受它们，但维护者无法在不重新打开每个差异的情况下浏览、评审或回退历史。

## 后果

- 大多数漫剧改动与官方代码隔离，因此官方更新通常只会涉及小而清晰的差异范围。
- 核心代码改动需要明确证据，并承担额外的升级验证。
- 本地仓库同时保留 `main` 和 `master`，两者的所有者和用途不同。
- 提交者花少量时间说明结果，以便后续维护者直接理解历史。
