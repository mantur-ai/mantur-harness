# Agent Note: 会话投影检查点保持请求顺序

Status: implemented

[English](2026-09-04-session-projection-checkpoint-order.md) | 中文

## Problem

会话创建与 `turn/end` 可能在很短时间内分别请求投影缓存检查点。每个请求都会同步捕获投影行，随后等待会话日志持久化屏障，再写入缓存记录。如果在等待前没有建立顺序，较新的请求可能先完成日志刷新和写入，之后较旧的创建切面再将其覆盖。即使较新的检查点没有报告错误，持久缓存也会持续陈旧。

## Decision

`SessionProjectionCache.write` 在调用时捕获投影行，并把完整的刷新与写入操作放进由该实时 `Session` 持有的队列。因此，请求会按调用顺序进入日志持久化屏障和存储域写入。失败的请求只结算自己的调用方，不会阻止后续排队请求运行。插件释放时会先移除事件生产方，再排空已捕获的检查点请求，最后关闭存储域。

队列以实时 `Session` 为键，而非仅以 id 为键。后续复用相同 id 的生命周期不会等待或继承此前生命周期的写入状态。

## Alternatives considered

**在刷新日志后捕获投影行。** 未采用，因为刷新等待期间事件仍可能进入实时投影。随后捕获可能写入由已完成持久化屏障之外事件派生的投影状态，让缓存领先日志。

**比较行水位并丢弃陈旧写入。** 未采用，因为一次检查点会以完整记录替换全部投影行。逐行比较会引入投影注册表与存储格式均未定义的合并语义。

**只依赖存储域写入链。** 未采用，因为各请求会在独立日志刷新完成后才进入该链。存储域保持的是抵达顺序，而不是更早的检查点调用顺序。

## Consequences

同一实时会话中重叠的必写检查点与节流检查点不能再使已存储投影切面倒退。不同会话的检查点仍彼此独立。每个调用方仍接收各自的写入失败，后台调用方仍会包含失败，后续排队请求仍能自行修复。会话日志、缓存文档格式、配置和公开服务 API 均不改变。聚焦测试会阻塞创建时刷新，同时让 `turn/end` 请求较新的检查点，并验证最终只保存较新的切面。
